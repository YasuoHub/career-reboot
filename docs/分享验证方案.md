# 分享验证 · 技术方案（微信 H5 场景）

> 背景：H5 里"分享解锁"机制的核心难题是——**如何确信用户真的分享给了 3 位好友，而不是 F12 改本地计数或重复刷**？
> 本方案给出三档可选实现，从轻到重。每档有明确 trade-off。
> 关联文档：[深度报告设计](./深度报告设计.md) §4 / [微信变现规划](./微信变现规划.md)

---

## 一 三档方案对比

| 方案 | 后端需求 | 防刷强度 | 转化率 | 推荐度 |
|---|---|---|---|---|
| **A. 客户端自增计数** | 无 | ⭐ 几乎为零 | 高（用户无感） | ❌ 不推荐上线 |
| **B. 带参链接 + 服务端推荐图谱** | 有（Vercel Serverless / Cloudflare Worker 都行） | ⭐⭐⭐⭐ 强 | 中（首次需授权） | ✅ **推荐 P0 上线用这个** |
| **C. 回调页面 + 人工审核** | 半自动 | ⭐⭐⭐ 中 | 低（用户嫌麻烦） | ❌ 仅作 B 的降级兜底 |

---

## 二 方案 A —— 纯前端（0 后端，不推荐上线）

### 实现
```js
// 用户点"我要分享" → localStorage.inviteCount = (localStorage.inviteCount||0) + 1
// 到 3 → 解锁标记
```

### 为什么不行
- 任何人开 devtools 直接 `localStorage.inviteCount = 100` 就解锁
- 微信对诱导分享的打击方式就是识别这类"自增解锁"模式，域名可能进黑名单
- 用于**内部测试/debug**可以，正式上线等于没做

## 三 方案 B —— 服务端推荐图谱（推荐生产用）

### 数据流（一次完整流程）

```
[1] 用户 A 在结果页点「邀请 3 位好友，解锁双人对比报告」
    ↓
[2] 前端请求服务端 GET /invite/token?uid=A_openid
    → 服务端返回 {token: "xxx", need: 3, progress: 0}
    ↓
[3] 前端生成带参链接
    https://www.career-turn.icu/?ref=A_openid&t=xxx
    → 弹出系统分享面板 / 生成专属海报二维码（走 H5 海报 Canvas）
    ↓
[4] 好友 B 点开链接
    → 前端检测 ?ref= 存在 → 上报 GET /invite/view?ref=A_openid&viewer=B_openid
    → 服务端记录"B 查看过来自 A 的链接"，但不计数（B 还没测）
    ↓
[5] B 走完 15 题，看到结果
    → 前端上报 POST /invite/complete {ref: A_openid, uid: B_openid, archetype: "..."}
    → 服务端：
       - 校验 B 是否是真实完成的新用户（有当日时间戳的测试记录）
       - 校验 B 不是 A 自己（防伪造）
       - A 的邀请进度+1（A_progress = min(3, A_progress+1)）
       - 返回给 B 一个"已被 @A 计入邀请进度"的提示（B 看到这行反而是社交货币："你邀请了 @猎手，获得一个解锁名额"）
    ↓
[6] 当 A_progress == 3 时：
    → 服务端写入 A 的 unlock 状态（Persist 30 天）
    → 下一次 A 打开结果页，前端查询 GET /unlock?uid=A_openid → true
    → 展示双人对比报告入口
```

### 服务端防刷规则（关键）

| 规则 | 说明 |
|---|---|
| R1 | 每个 `A_openid` 的 ref 只对每个新完成用户计 1 次——同一 viewer 不能给同一 A 贡献两次 |
| R2 | 被推荐人 `B_openid` 必须是"当日新完成测试"的——老用户重测不算（防自己用小号刷）|
| R3 | `A_openid != B_openid`——通过 unionId 强比对，不用 openid 因为同主体多个小程序 openid 不同 |
| R4 | 每天每个 A 最多累计 N 次（比如 5）——超出不再累加，但保留自然增长空间（防脚本刷）|
| R5 | 服务端按日去重：一个 B 一天内只能给 X 个不同的 A 提供一次有效贡献（防小号池）|

### OpenID 获取（H5 场景标准做法）

```js
// 微信网页授权拿 openid：需要一个已认证的服务号或公众号
// 短链跳转流程：
// ① 用户点"解锁"按钮 → window.location.href =
//      `https://open.weixin.qq.com/connect/oauth2/authorize?
//        appid=YOUR_APPID&redirect_uri=${encodeURIComponent(callback)}
//        &response_type=code&scope=snsapi_base#wechat_redirect`
// ② 微信跳回 callback URL，带 ?code=xxx
// ③ 前端把 code 发给后端，后端换 access_token + openid（用 appsecret）
// ④ openid 存入 session/localStorage，下次直接复用
```
- 需要**已认证的微信服务号**（订阅号没有网页授权能力）。用户有微信经营账户，应该能申请到。
- 也可以考虑换成「小程序」路线（用户的产品本身更适合做小程序，走 `wx.login()` 直接拿 openid 无感知）——这是个大的产品决策点，见第四节。

### 服务端落地方案（三选一，都支持）

| 选择 | 优点 | 缺点 |
|---|---|---|
| **Vercel Serverless Functions** | 跟现有静态站同域，部署简单 | 免费档函数调用 10 万次/月，后续按量付费 |
| **Cloudflare Workers + KV** | 免费额度慷慨，全球 CDN | 要配独立域名 CNAME |
| **Supabase Edge Functions + Postgres** | 全托管 DB + 免登录鉴权 | 免费档 DB 500MB 够用但扩容要看单价 |

**推荐**：Vercel Serverless（跟现有部署零切换成本）+ Supabase Postgres（存 invite 表，结构最简单：3 列 ref_uid / viewer_uid / created_at）。

## 四 一个更大的产品决策要不要现在做

如果你能拿到微信**小程序**资格，整个分享验证可以简化为：

```
用户在小程序测完 → 生成带参数的小程序码（scene="ref=xxx"）
→ 好友扫这个码进入小程序 → 自动上报 ref=xxx + 自己 openid
→ 服务端同方案 B 逻辑
```

**优势**：
- 小程序内 `wx.login()` 拿 openid **无感知**（不用网页授权那套跳转）
- 小程序码天然就是可传播的图片（比 H5 海报二维码更原生）
- 微信生态内裂变更顺滑

**劣势**：
- 需要重新开发一版小程序（可以复用现有 data.js / app.js 逻辑，只是壳换掉）
- 小程序要审核上线（首次审核 ~1 周）
- H5 版仍然保留作为传播入口

**建议路径**：
1. 现在先用 H5 + 方案 B 快速验证付费意愿（1~2 周）
2. GMV 稳定后再决定是否上小程序版（如果分享裂变效果显著，小程序值得投）

## 五 文案的合规边界（容易踩雷的地方）

微信对"分享获利"的定义很严，**以下措辞不能出现在解锁引导里**：

| ❌ 禁止 | ✅ 替代 |
|---|---|
| 「分享给 3 位好友**免费解锁**」 | 「邀请 3 位好友测完，你获得一份**双人对比报告**」 |
| 「分享**得好处**」 | 「测完他们的结果跟你比对，看看你们适合合伙还是师徒」 |
| 「分享给好友**即可领取**」 | 「邀请好友一起测，互相补完 6 维画像后得到组合报告」 |
| 任何出现「免费/解锁/领取」字眼在分享引导里 | 完全删掉，用"获得一份新增报告"中性表达 |

**核心原则**：分享解锁物本身必须是有独立价值的产物（双人对比报告），而不是把原本收费的"单人深度报告"通过分享白送。一旦后者发生，被识别为诱导分享的概率飙升。

## 六 埋点与监测（P0 就要埋）

分享解锁成功时上报这些维度到 GA4（或自建简单统计）：

```
event: share_unlock_success
props:
  - unlocked_by: 'pay' | 'share'
  - archetype_id: 'ei_at_jp_1'
  - archetype_cn: '猎手'
  - invite_chain_len: 3          // 分享链长度，帮助判断是否二级裂变
  - hours_to_unlock: 3600        // 从点击分享到解锁的耗时
  - gender: '男' | '女' | '其他'
```

**关键指标**：
- 分享解锁 vs 付费解锁的比例 → 判断裂变机制是否被用户接受
- 平均邀请链长度 → 判断有没有二级分享
- 已解锁用户的后续留存（7 天内回到站点）→ 判断报告本身是否有复看价值

这些数据如果跑得好，双人对比报告的 P1 就可以放心投入。

## 七 P0 交付最小版本（给接下来开发用）

最小可用集（不追求防刷极致，先跑通）：

1. **Vercel Serverless Function × 2**
   - `/api/invite/token`：生成/返回 invite token
   - `/api/invite/complete`：记录一次有效推荐，前置 R1/R2/R3 三个校验
2. **Supabase 一张表**
   ```sql
   create table if not exists invites (
     id bigint generated by default as identity,
     referrer_unionid text not null,
     viewer_unionid text not null,
     created_at timestamptz default now(),
     unique(referrer_unionid, viewer_unionid)  -- R1 防重
   );
   ```
3. **前端两个入口**
   - 结果页加"邀请 3 位好友解锁双人对比"按钮 → 拉起分享面板（首选微信 JS-SDK `updateAppMessageShareData`；兜底就是分享链接 + 用户手动粘贴）
   - 报告解锁判定：`GET /api/unlock?uid=xxx`，true 时直接渲染双人对比

P0 可以先不做 R4/R5（防重度机器刷），先让真实用户的使用数据说话；如果发现刷量再补。
